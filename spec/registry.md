# Meld Pack Registry and Signing Specification (Phase 7)

Status: normative for Phase 7. Derived from `project.md` §4 (Lang Pack
contract), §7 (tooling), §9 (security), §11 (ecosystem). Implemented by
`tools/packtool.py`; every decision marked **JUDGMENT CALL** is binding until a
later phase explicitly changes it.

The goal is narrow: a third party can publish, discover and install a Lang Pack
as **data**, with integrity checks, and without touching `crates/` or any
existing language pack. The registry has no server, no network and no package
manager semantics; it is a checked-in directory that can be mirrored like any
other source tree.

This spec governs pack integrity and the checked-in registry format. Installable
Lang Libraries are the next layer: `spec/libraries.md` adds `library.toml`, a
git-backed terminal installer, a shared installed index and a per-project
`meld.lock`. `meld-pack` reuses the verification rules below verbatim rather
than defining a second integrity format.

## 1. Integrity files in a pack

Each pack carries two extra files next to `pack.toml`:

```
checksums.sha256      # SHA-256 of every payload file
signature.ed25519     # public-key Ed25519 signature over checksums.sha256
```

### 1.1 `checksums.sha256`

One line per payload file:

```
<64 lowercase hex chars>  <posix-relative path>
```

Exactly two spaces separate the digest from the path; paths are relative to the
pack root, use `/`, and contain no `..` or absolute prefix. Lines are sorted by
path and terminated with LF. `packtool.verify` rejects a file that is not in
this canonical form.

Excluded from checksumming (they cannot checksum themselves and are control
metadata): `checksums.sha256`, `signature.ed25519`, caches (`__pycache__`,
`.mypy_cache`, `.pytest_cache`, `.git`, `target`), and `*.pyc`/`*.pyo`.
**JUDGMENT CALL:** excluding caches makes a pack's digest reproducible from its
source files. Symlinks are rejected rather than followed: following one could
make a published pack read outside its own directory (project.md §9).

`pack.toml` may set `strict = true`. Then both files are mandatory for
`verify` and `publish`; a missing one is an error, not a warning. Non-strict
packs still require `checksums.sha256` (there is nothing to verify without it)
but may omit `signature.ed25519`. **JUDGMENT CALL:** strict packs additionally
require an immutable `[tree_sitter].rev`: either an opaque `pinned:<ref>` or an
exact crate version such as `0.25.0` (optionally `=0.25.0`). Both spellings are
honest pins; a floating ref like `main` or the word `pinned` is rejected. The
checked-in grammar packs use the exact-version form because
`tools/sync_grammars.py` reads that field as a crate version, matching
`lang-pack.md` §2/§6.

### 1.2 `signature.ed25519`

Exactly one LF-terminated line:

```
meld-pack/ed25519/v1 <key-id> <128 lowercase hex chars>
```

- `key-id` is the first 16 hex chars of SHA-256 over the 32 raw public-key
  bytes. It identifies a key without revealing it and lets a verifier reject
  an unknown or revoked signer early.
- The signature is Ed25519 over **exactly** these bytes:

  ```text
  b"meld-pack/ed25519/v1\n" + pack-id + b"\n" + version + b"\n" + raw bytes of checksums.sha256
  ```

  There is no JSON wrapper, normalization, or extra newline: the checksum
  file's own trailing LF is the final byte. Rust (`ed25519-dalek`, strict
  verification) and Python (`cryptography`) implement the same byte sequence.
- The signature covers the checksums file, which in turn commits to every
  payload file. It does not cover itself.

**JUDGMENT CALL (major):** HMAC-SHA256 was cut over to public-key Ed25519. A
symmetric key cannot be a public trust root: everyone who can verify can also
forge. Ed25519 gives verifiers an immutable public key while the private key
stays outside every repository and worktree. Consequences:

- Private keys are generated by `packtool keygen`, stored outside the repo with
  mode `0600`, and passed explicitly with `--private-key`. No private key,
  seed, or `meld-keys` directory is ever checked in.
- Verification reads public `trust-roots.toml` and optional `revocations.json`.
  A well-formed signature without a trust root is reported as
  `present-unverified`, never as authentic. `require_trusted` turns that into a
  hard failure; remote installs set it by default.
- Rotation is additive: add a new public key to `trust-roots.toml` and sign
  with its private key. Revocation is explicit: add the old key-id to
  `revocations.json`. A revoked id is rejected before signature math.

## 2. Registry format

A registry directory:

```
<registry>/
  index.json              # canonical JSON, sorted keys, no timestamps
  trust-roots.toml        # meld-trust-roots/1 public keys
  revocations.json        # meld-revocations/1 revoked key ids
  mirrors.json            # meld-registry-mirrors/1 canonical mirror labels
  attestation.ed25519     # signed commitment to the four files above
  packs/<id>/<version>/   # complete pack copies created by publish (optional)
```

`index.json` schema `meld-pack-registry/1`:

```json
{
  "schema": "meld-pack-registry/1",
  "packs": [
    {
      "id": "shell",
      "version": "0.1.0",
      "aliases": ["posix-sh", "sh"],
      "tier": "T2",
      "level": "L1",
      "strict": true,
      "path": "../../tests/fixtures/pack-third-party",
      "checksums_sha256": "<sha256 of that pack's checksums.sha256>",
      "signature": {
        "scheme": "meld-pack/ed25519/v1",
        "key_id": "<16 lowercase hex chars>",
        "signature": "<128 lowercase hex chars>"
      }
    }
  ]
}
```

Rules:

- `id` and `version` match `^[A-Za-z0-9][A-Za-z0-9._-]*$`; `version` defaults to
  `0.0.0` for pre-registry packs. `path` is POSIX-relative and points at a
  complete pack directory. By default it must stay inside the registry. A
  **valid attestation** additionally allows `../` paths so the checked-in
  registry can point at sibling packs without duplicating data. The shipped
  `packs/registry/index.json` has 29 entries: `../<id>` for the 28 bundled
  packs and `../../tests/fixtures/pack-third-party` for the worked example.
- `signature` is `null` for unsigned (necessarily non-strict) packs.
- The index is written with sorted keys and **no timestamps**, so repeated
  publishes of identical content are byte-for-byte reproducible (project.md
  §9). Entries are sorted by `(id, version)`.
- `publish` copies a pack to `packs/<id>/<version>/` and adds an entry. The
  checked-in registry intentionally ships no staged copies; it references the
  real pack directories instead, which keeps the repo free of duplicate data
  and keeps `install` honest (an entry always has bytes to verify).
- **JUDGMENT CALL:** publishing an existing `id`/`version` with identical
  integrity data is idempotent; publishing *different* content at the same
  coordinates is rejected. Bump the version instead, because consumers pin
  versions.
- **JUDGMENT CALL:** an exact id match wins over aliases. The registry contains
  both `bash` (alias `shell`) and the third-party `shell` pack; without this
  rule the pack's own id would be unaddressable. When no id matches, a unique
  alias resolves; an alias used by two different ids is an error, never a
  guess.

### 2.1 Trust roots, revocations, mirrors, attestation

`trust-roots.toml` is canonical TOML with schema `meld-trust-roots/1` and one
`[[keys]]` block per signer:

```toml
schema = "meld-trust-roots/1"

[[keys]]
key_id = "8ec9528bf1f0e31f"
public_key = "cf4af2da869998ad10eedf04be673ddcb52fe55e26cb62e0033188e5c1754e87"
label = "Meld Ed25519 release key"
created = "2026-11-20"
```

`revocations.json` has schema `meld-revocations/1` and a `revoked` list of
`{key_id, reason, revoked}` objects. `mirrors.json` has schema
`meld-registry-mirrors/1` and a sorted `mirrors` list. Both are canonical JSON
(sorted keys, two-space indent, trailing LF).

`attestation.ed25519` is the same one-line shape as a pack signature, with
scheme `meld-registry/attestation/ed25519/v1`. It signs a canonical digest map
of `index.json`, `trust-roots.toml`, `revocations.json` and `mirrors.json`, so
swapping metadata without re-signing is detected by `verify-registry`. The
attestation signer must itself be an unrevoked trust root.

## 3. CLI

```
python3 tools/packtool.py verify <pack-dir> [--trust-roots <file>] [--revocations <file>] [--require-trusted]
python3 tools/packtool.py sign <pack-dir> --private-key <file>
python3 tools/packtool.py publish <pack-dir> --registry <dir> [--trust-roots <file>] [--revocations <file>]
python3 tools/packtool.py list --registry <dir> [--json]
python3 tools/packtool.py install <lang> --registry <dir> --into <dir> [--trust-roots <file>] [--revocations <file>] [--require-trusted]
python3 tools/packtool.py keygen --private-key <file> --public-key <file> [--force]
python3 tools/packtool.py trust-roots init|add --trust-roots <file> --public-key <file> [--label <text>] [--created YYYY-MM-DD]
python3 tools/packtool.py revocations init|revoke --revocations <file> [--key-id <id>] [--reason <text>] [--revoked YYYY-MM-DD]
python3 tools/packtool.py mirrors --registry <dir> --mirror <label> [--force]
python3 tools/packtool.py attest --registry <dir> --private-key <file> [--trust-roots <file>] [--revocations <file>] [--mirrors <file>]
python3 tools/packtool.py verify-registry <dir> [--trust-roots <file>] [--revocations <file>] [--verify-packs]
```

- `verify` checks payloads against `checksums.sha256`, then the signature.
  Without trust roots it reports presence only; with them it reports
  `verified`, `unknown key`, `revoked`, or `signature mismatch`. It prints a
  short report ending in `OK`.
- `sign` writes `signature.ed25519`; it refuses a stale/malformed checksums
  file and a private key located inside the pack. `--key` is removed with an
  explicit migration error.
- `publish` verifies first, copies the pack to `packs/<id>/<version>/`, then
  updates `index.json` with the signature metadata.
- `list` prints one row per pack; `--json` emits the raw index for tooling.
- `install` resolves an id or alias, verifies the registry attestation when
  present, checks index metadata against the staged pack, copies it to
  `<into>/<id>`, and verifies the copy. `--require-trusted` makes Ed25519
  verification mandatory.
- `keygen`, `trust-roots`, `revocations`, `mirrors`, `attest` and
  `verify-registry` are the key lifecycle and registry metadata commands.
- Exit codes: `0` success, `1` integrity/validation failure, `2` argparse usage
  error. All expected failures are printed as `packtool: error: ...` on stderr.

**JUDGMENT CALL:** `install` refuses to overwrite an existing target. It is a
data copy, not a package manager; no uninstall/upgrade machinery is implied.

## 4. Trust model

| Actor | Power | Defense |
| --- | --- | --- |
| Pack author | supplies pack data and plugins | checksums detect changes after publication; Ed25519 binds checksums to a public key |
| Registry maintainer | edits index and metadata files | signed attestation binds all metadata; canonical JSON is reviewable in version control |
| Key custodian | holds a private key outside the repo | keygen enforces mode `0600`; signing refuses a key inside a pack; revocation rejects a compromised id |
| Installer | chooses registry, trust roots, target dir | remote installs require a verified signature; strict packs always carry one; never overwrites |
| Worker/runtime (future) | executes pack code | out of scope for packtool; OS sandbox and pack `sandbox` rules come from project.md §9 / `lang-pack.md` §6 |

Hard rules for registry tooling:

- **No network access** and no downloads.
- **No toolchain installation.** `toolchain.toml` is copied as data;
  `meld doctor` reports, never installs (project.md §9).
- **No pack code execution.** `packtool` never imports a worker, `marshal`
  module or end scanner, and never spawns a process from pack content.
- **No implicit trust in the index.** Index metadata is validated against the
  staged pack before a copy is made; `../` paths require a valid attestation.
- Public trust roots are the authenticity boundary. A signature that is merely
  well-formed is labelled `present-unverified`; local development may proceed
  with it, but provenance requires `--trust-roots` and a non-revoked key.

## 5. Failure modes

| Condition | Result |
| --- | --- |
| `checksums.sha256` missing | error for verify/publish/install (explicitly required for strict packs) |
| Checksums malformed, unsorted, duplicate path, unsafe path, non-LF | `malformed checksums.sha256` / `not canonical` |
| Payload edited after checksumming | `checksum mismatch: <path>` |
| File added or removed | `unexpected file(s): ...` / `missing file(s): ...` |
| Symlink inside pack | `symlink in pack is not allowed` |
| `strict = true` without `signature.ed25519` | `strict pack requires signature.ed25519` |
| Malformed signature line | `malformed meld-pack/ed25519/v1 signature` |
| Modified checksums, pack id or version | `signature mismatch` |
| Unknown key-id | `is not in the trust roots` |
| Revoked key-id | `is revoked` |
| Missing/malformed trust roots or revocations | `trust roots not found` / `invalid trust roots` / schema error |
| `--require-trusted` without verification | `trusted Ed25519 signature required` |
| Private key inside pack, or `--key` | `private key file must not be inside the pack` / `HMAC --key was removed` |
| Unpinned grammar rev on a strict pack | `strict pack requires a pinned [tree_sitter].rev` |
| Invalid `pack.toml` / unknown tier or level | descriptive `invalid pack.toml` / `unknown tier`/`level` |
| Unknown id/alias, or ambiguous alias | `unknown language or alias` / `ambiguous alias` |
| Registry index missing / wrong schema / corrupt JSON | `registry index not found` / `unsupported registry schema` / `invalid registry index` |
| Attestation mismatch or tampered metadata | `registry attestation mismatch` |
| Index checksum/signature disagrees with staged pack | `registry index ... does not match the staged pack` |
| Install target exists | `install target already exists` |
| Different bytes at an existing id/version | `different pack already published ...; bump version` |

## 6. Adding a language without touching the Rust core

This is the Phase 7 done-when criterion (project.md §11). No file under
`crates/` and no existing `packs/<language>/` directory is modified.

1. Write a pack directory containing `pack.toml`, `runner.toml`,
   `toolchain.toml`, a worker (if `level >= L1`), `region_end.*`, and `tests/`
   as specified by `lang-pack.md`. A language with no runnable CLI stays L0;
   say so in its README (project.md §5 honesty note).
2. Add `library.toml` with `api = "meld-lang-library/1"`, `kind = "lang"`,
   matching `id`/`version`/`aliases`, and relative `exports`
   (`spec/libraries.md` §2). `tools/gen_pack.py` does this for new packs;
   `tools/make_libraries.py` does it for existing ones.
3. Generate a key pair outside the repo with `packtool keygen` if you do not
   have one. Run `packtool sign <pack-dir> --private-key <file>` after
   generating `checksums.sha256`; `strict = true` requires both files.
4. Add the public key to `trust-roots.toml` with `trust-roots add` (rotation),
   run `packtool publish`, then `packtool attest` to bind the updated metadata.
5. Consumers can use either `packtool list/install` against a local registry
   or `meld-pack remote-list/install` against a git source; the latter is the
   installable Lang Library workflow in `spec/libraries.md`.
6. Runtime discovery of `runner.toml` is the integration point for the Rust
   runner; it reads the manifest and launches the declared worker.
7. `tests/fixtures/pack-third-party/` is a complete worked example for a
   `shell` pack (a language absent from the existing packs). It is data-driven:
   its conformance cases live in `tests/conformance.json`, not in code.

**JUDGMENT CALL:** the registry stores only pack data and metadata; generator
polish and automatic grammar downloads remain out of scope. The registry
tooling is deliberately usable before any Rust changes exist, so third-party
packs can be reviewed as plain files.

## 7. Judgment call index

1. Ed25519 with public trust roots, not HMAC; the signed message is exactly
   scheme + id + version + raw checksum bytes. Key ids are SHA-256 prefixes of
   raw public keys; revocation is explicit (§1.2).
2. Canonical checksums (sorted, LF, two spaces); caches and control files
   excluded; symlinks rejected (§1.1).
3. Checksums always required; signature required only for `strict` packs;
   strict also requires an immutable grammar rev (`pinned:<ref>` or exact
   version) (§1).
4. Canonical, sorted, timestamp-free registry JSON; relative paths, with `../`
   allowed only under a valid attestation; idempotent republish and version
   bumps for changed bytes (§2).
5. Exact id wins over aliases; otherwise a unique alias resolves, and a
   collision is an error (§2).
6. A signed attestation binds index, trust roots, revocations and mirrors so
   metadata cannot be swapped unnoticed (§2.1).
7. Install is a non-overwriting data copy: no network, no toolchain install,
   no pack code execution, no implicit trust in the index (§3–§4).
8. Remote installs require a verified signature by default; local checks can
   report `present-unverified` but never call it authentic (§4).
9. A pre-version pack publishes as `0.0.0`; `tomllib` means Python 3.11+ is
   required, and Ed25519 primitives come from `cryptography` (§1/implementation
   header).
